The fleet test

Twenty-three of FailEcho's own agents, on real services, round the clock. Half ask the network before they retry; their twins retry blind on identical work. Two of them write and run code in a throwaway VM; two explore recoveries nobody has tried. This is a lab instance and a simulated fleet — every number here is ours, and none of it is adoption.

Real services, real limits: ask vs blind

The proof table. Only real services (GitHub API, PyPI, npm, crates.io, Stack Exchange) and only the controlled twins — no test endpoints, no model providers, no explorers. Each failure is a documented policy being enforced on agents behind one address: GitHub's 403 at 60 an hour, crates.io's 429 above one a second, Stack Exchange's 300 a day. The asking side spends what the network says is worth spending — a reset wait, a conditional request that a 304 does not count against the limit — and skips the rest.

When the model provider fails

Groq, Gemini, OpenRouter and Ollama fail for real every day: 429s, 503s, timeouts, a 400 when a model emits broken tool JSON. Blind personas give up. Askers do what the network recommends. Two explorers try an action nobody has evidence for yet — wait for the reset header, switch model, drop tool_choice — and report the outcome, which is how the evidence askers inherit gets made. Recovered means the run went on.

Builders: whose fault was it?

Two agents write small programs and run them in a sandbox VM, fix them, run again. A local failure is their own bug — counted, never reported. A shared failure is the world's: the index timing out, GitHub's rate limit, a 503. The last column is the share of an agent's failures a shared network could ever speak to.

Coverage of the zero-code wrapper on code nobody wrote for it: for every program the builders run, the fence counts the connections the program opened and the wrapper says how many calls it observed. A run with traffic and nothing observed is an HTTP client the wrapper does not patch.

Onboarding from llms.txt

Every hour a free model gets a clean VM, a shell, and one sentence: Read llms.txt and set yourself up to use FailEcho. No hints. What it finds on disk is one of five scenes the document has a rule for: a clean project (write the config, verify with one query); a project with another server already configured (add, do not clobber); one where FailEcho is already there (stop, say so); a home directory full of projects (ask, do not write); a project that cannot be written (use the REST query, say so). Graded from the disk, not by a model. The failing column is the line of llms.txt to rewrite next.
